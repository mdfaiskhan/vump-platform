# ADR-010 — Firebase Platform Integration

- **Status:** Accepted
- **Date:** 2026-08-09
- **Supersedes:** none

## Context

Firebase is the intended provider for several cross-cutting capabilities — authentication, crash reporting, analytics and push messaging. Each arrives as a separate plugin, but all of them depend on one prior step: the Firebase platform must be initialised before any of them can be used.

Two failure modes follow from getting that step wrong, and both are cheap to prevent now and expensive to unpick later.

The first is **initialisation scattered across features**. If each product initialises on first use, initialisation order becomes implicit, the widget tree acquires an async dependency it should not have, and a second call to `Firebase.initializeApp` throws rather than no-ops.

The second is **the platform leaking into the application**. If features import `firebase_core` directly, Firebase stops being a replaceable dependency and becomes a structural assumption.

A third question needed settling before any code was written: whether the generated `firebase_options.dart` may be committed at all, given ADR-007's prohibition on Firebase secrets in source.

## Decision

### `firebase_core` only, for now

Only `firebase_core` is declared. Product plugins are added by the missions that implement them, not in advance. An unused dependency is weight in the build and a version to maintain.

### Initialisation is owned by `core/firebase/`

Per ADR-002 this is cross-cutting infrastructure. `FirebaseInitializer` is the sole owner of platform startup.

### Initialisation happens exactly once, asynchronously, outside the widget tree

The initialiser holds the in-flight `Future`, not merely the resulting app, so concurrent callers during startup share one initialisation rather than racing — the same pattern ADR-009 requires of `DatabaseService`. A `duplicate-app` error is treated as success and the existing instance adopted, which is what hot restart produces.

Initialisation is awaited in the composition root before `runApp`. No widget triggers it.

### The initialiser knows nothing about Firebase products

It initialises the platform and stops. Auth, Crashlytics, Analytics and Messaging each resolve the already-initialised default app through the SDK's own registry, so adding a product means adding a dependency and a provider for it — never editing initialisation code. There is nothing product-specific in the initialiser to edit.

Product providers depend on `firebaseAppProvider`, so ordering is expressed as a dependency rather than assumed.

### The generated options file is committed; secrets still are not

`firebase_options.dart` is generated by `flutterfire configure` and committed. Its contents — API key, app ID, project ID, sender ID — are **client identifiers, not credentials**. Firebase protects projects with Security Rules and App Check, not by concealing these values, and they are extractable from any shipped binary regardless.

They therefore fall under ADR-007's *permitted* category, alongside base URLs: disclosure reveals nothing that running the application does not.

ADR-007's prohibition is unchanged and absolute for service account keys, server keys and admin credentials. Those are backend artefacts and must never enter the repository.

### Failures enter the existing error taxonomy

`FirebaseInitializationException` extends `AppException`, so no SDK `FirebaseException` escapes the layer — the boundary `DioClient`, `SecureStorageService` and `DatabaseService` each maintain for their own packages. Lifecycle events and failures are logged through `AppLogger`, and the environment from ADR-006 is recorded so a support report shows which project a session used.

## Alternatives Considered

- **Initialise in `main.dart` directly, with no initialiser class** — rejected. It works for one product and degrades as soon as failure handling, logging, timeouts and duplicate-app tolerance are needed; all of that then lives in the composition root.
- **Initialise lazily on first product use** — rejected. Makes ordering implicit, pushes an async dependency into the widget tree, and turns a configuration error into a failure at an arbitrary later moment.
- **Add all product plugins now** — rejected. Unused dependencies with no consumer to validate them.
- **A `FirebaseService` wrapping each product behind application-owned interfaces** — rejected as premature. The right abstraction depends on what each product is used for, and inventing it before the first consumer would guess.
- **Keep `firebase_options.dart` out of version control** — rejected. It would break every clean checkout and every CI build to protect values that are not secret, while creating the impression that the real secrets are handled the same way.
- **Supabase or a self-hosted equivalent** — out of scope. Firebase is directed by the project plan; this record covers integration, not selection.

## Consequences

- Firebase has exactly one initialisation site, and duplicate initialisation is impossible.
- Adding a Firebase product does not modify existing code.
- `firebase_core` is confined to `core/firebase/`, so the platform is replaceable at the cost of one layer.
- **A third asynchronous startup prerequisite now exists**, alongside secure storage (ADR-008) and the database (ADR-009). The composition root has to await all three, and the router needs a genuine loading state. This is no longer a minor consideration; it is the shape of application startup.
- Initialisation is bounded by a timeout. A misconfigured build fails cleanly instead of hanging on a blank screen.
- Native configuration files — `google-services.json` and `GoogleService-Info.plist` — are required in the platform directories. Without them the platform SDKs will not initialise no matter what Dart does.
- Two deviations from the Mission 0.10 taxonomy were forced by path scope and should be corrected when `core/errors/` is next in scope: `FirebaseInitializationException` sits in `core/firebase/` rather than `core/errors/exceptions/`, and it uses `ErrorCode.unknown` because no `firebaseInitializationFailed` case exists in the enum.
- Committing client identifiers means the Firebase project is identifiable from the repository. This is expected and is why Security Rules and App Check, not obscurity, are the protection — configuring them is a backend obligation this decision does not discharge.

## Implementation Status

**Implemented and integrated on Android. Verified in Mission 0.15.3.**

1. ~~`firebase_options.dart` is a placeholder.~~ **Done.** Generated against project `vump-platform-f86af` and located at `lib/core/firebase/firebase_options.dart`, per ADR-002. `firebase.json` now targets that path, so regeneration preserves the location.
2. ~~The native configuration files are absent.~~ **Android done, iOS outstanding.** `android/app/google-services.json` is present and consistent with the Dart options, and the `com.google.gms.google-services` plugin is applied in both `settings.gradle.kts` and `app/build.gradle.kts`. `ios/Runner/GoogleService-Info.plist` has **not** been generated; the iOS app is registered in the Firebase project but the file was never written.
3. ~~Nothing awaits `firebaseAppProvider`.~~ **Done.** `lib/main.dart` builds the `ProviderContainer`, awaits `firebaseAppProvider` before `runApp`, and passes the container to `UncontrolledProviderScope`. No widget triggers initialisation.

Verified by static check and by test: exactly one `Firebase.initializeApp` call site, exactly one awaiting call site, no `firebase_core` import outside `core/firebase/`, and concurrent callers provably share one initialisation attempt.

Missions 0.15, 0.15.1 and 0.15.2 are complete. What remains is platform configuration rather than architecture: the iOS plist, and the placeholder `com.example.mobile` application identifier.

### Provisional: startup tolerates initialisation failure

`main.dart` catches `AppException` from initialisation, logs it as an error, and continues to `runApp`.

This is **not** a decision that Firebase is optional. It exists because no feature depends on Firebase yet, so a build that starts without the platform is degraded in theory and identical in practice. iOS is also not fully configured, so aborting on failure would make the application unrunnable there while nothing yet depends on it.

The original justification — that the project was unconfigured — expired in Mission 0.15.2. The tolerance now rests solely on there being no dependent feature, which is a weaker footing and a shorter fuse.

When the first Firebase-dependent feature lands, starting without Firebase stops being degraded operation and becomes silent breakage. At that point the tolerance must either be removed, making initialisation fatal, or be replaced by an explicit degraded-mode decision recorded in its own ADR. It must not be allowed to persist by inertia.
