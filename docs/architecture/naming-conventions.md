# Naming Conventions

The canonical naming standard for the Vump Technologies repository.

Governed by **ADR-023**. Where this document and the ADR disagree, the ADR governs.

## How to read this document

Every rule states the **convention**, **why** it exists, **examples**, the **common mistake**, and **exceptions**. A rule with no reason is a habit, and habits are abandoned the first time they are inconvenient.

**This document does not restate rules that live elsewhere.** Where a convention is already fixed by an accepted ADR, by `CLAUDE.md`, or by a lint rule in `mobile/analysis_options.yaml`, this document cites it and adds only what is missing:

| Already fixed by | What it fixes |
|---|---|
| `CLAUDE.md` | `snake_case` filenames, `PascalCase` classes, `camelCase` variables, one public class per file |
| ADR-021 · `analysis_options.yaml` | Mechanical enforcement — `file_names`, `camel_case_types`, `camel_case_extensions`, `non_constant_identifier_names`, `constant_identifier_names`, `library_prefixes`, `always_use_package_imports` |
| ADR-022 · `folder-structure.md` | Folder placement and feature directory naming |
| `docs/architecture/README.md` | ADR filenames and the ADR section template |
| ADR-019 · `branching-strategy.md` | Branch names |
| ADR-020 · `commit-conventions.md` | Commit types and scopes |
| ADR-011, ADR-012 | S3 bucket names and the object key schema |
| ADR-007, ADR-014, ADR-018 | Environment names, `APP_ENV` keys, AWS slugs |
| ADR-005 | Theme token file and class names |

**The governing principle.** A name is a contract about *what kind of thing* something is. `SessionRepository` promises an interface a fake can replace; `SessionService` promises a concrete mechanism. When the suffix and the reality disagree, every reader is misled and the compiler says nothing. Names are checked by people, which is why the vocabulary must be small enough to remember.

## 1. Files and folders

### 1.1 Dart files

**Convention.** `snake_case.dart`. The filename is the `snake_case` form of the single public declaration it contains.

**Why.** `CLAUDE.md` requires one public class per file, so the filename can be a total function of that class — which means a reader who knows the class name knows the path without searching, and the analyzer can enforce the format (`file_names`). Case-insensitive filesystems on Windows and macOS make `PascalCase` filenames a portability hazard: two files differing only in case collide.

**Examples.**

| Declaration | File |
|---|---|
| `DioClient` | `dio_client.dart` |
| `SecureStorageRepository` | `secure_storage_repository.dart` |
| `AppSemanticColors` | `app_semantic_colors.dart` |

**Common mistake.** Naming the file after the folder it sits in and letting the class drift — `providers/database_provider.dart` legitimately holds six providers (see §4.1), but a file called `network.dart` holding `DioClient` is unfindable.

**Exceptions.** Files whose only public declarations are top-level variables — provider files (§4.1) — are named for their subject plus the role: `dio_provider.dart`, `logger_provider.dart`. Generated files take the generator's name: `<source>.g.dart`, `<source>.freezed.dart`. `firebase_options.dart` is generated by `flutterfire` and is not renamed.

### 1.2 Folders

**Convention.** `snake_case`, singular for a subject, plural only for a directory of peers.

**Why.** Directory names appear in every `package:mobile/...` import, so they are read far more often than they are written. The singular/plural split carries information: `core/network/` is one subject; `core/network/interceptors/` is a set of interchangeable things.

**Examples.** Singular subjects — `core/network/`, `core/database/`, `core/logging/`. Plural peer sets — `interceptors/`, `providers/`, `collections/`, `migrations/`, `exceptions/`, `interfaces/`.

**Common mistake.** `utils/`, `helpers/`, `common/`, `misc/`. Forbidden by ADR-022 R5 — a directory whose name describes nothing accumulates everything.

**Exceptions.** Feature directories are the capability name as a user would say it (ADR-022 §2.4), which is singular even though a feature is not a subject: `features/recording/`, not `features/recordings/`.

### 1.3 Test files

**Convention.** `<subject>_test.dart`, at the path mirroring the file under test.

**Why.** `flutter test` discovers `*_test.dart`. Mirroring the path means the test for `lib/core/network/dio_client.dart` is at `test/core/network/dio_client_test.dart` and nowhere else, so a missing test is visible as a missing file rather than something to search for.

**Examples.** `test/app/config/app_environment_test.dart`, `test/core/firebase/firebase_initializer_test.dart`.

**Common mistake.** `test/dio_client_test.dart` — flat, so coverage gaps become invisible once there are more than a dozen tests.

**Exceptions.** None. A test that spans several files is named for the behaviour it covers and placed at the path of the file that owns that behaviour.

### 1.4 Documentation files

**Convention.** `kebab-case.md`, except `README.md`, which is uppercase because tooling and GitHub look for that exact name.

**Why.** Kebab-case is the web convention, survives URLs without escaping, and is what `docs/architecture/README.md` already fixes for ADR filenames — extending it to every document means one rule rather than two.

**Examples.** `folder-structure.md`, `naming-conventions.md`, `branching-strategy.md`, `secrets-management.md`, `volume-amendments.md`, `aws-sdk-integration.md`.

**Common mistake.** `Title_Case_With_Underscores.txt`. **The repository has exactly one violation:** `docs/Teams_work.txt` — wrong case, wrong separator, wrong extension, and at the root of `docs/` rather than in a subdirectory. Recorded in §11.

**Exceptions.** `README.md`, `LICENSE`, `CLAUDE.md` — fixed by convention outside this project.

### 1.5 ADR files

**Convention.** `ADR-NNN-kebab-case-title.md`, already fixed by `docs/architecture/README.md`.

**Why and examples.** See that document. It is the authority; this section exists only so a reader looking for ADR naming finds the pointer.

**One addition.** The title describes the **decision**, not the topic — `ADR-003-state-management-riverpod.md`, not `ADR-003-state-management.md`. A reader scanning the directory should be able to tell what was decided without opening anything.

### 1.6 Infrastructure files

**Convention.** `kebab-case`, with the environment as the final segment: `<subject>-<environment>.<ext>`. Templates take a `.tmpl` suffix after the real extension.

**Why.** The environment last makes `ls` group by subject rather than by environment, so the three variants of one policy sit together and a missing one is obvious. `.tmpl` after the extension keeps editors syntax-highlighting the file as JSON.

**Examples.** `lifecycle-prod.json`, `bucket-policy-staging.json`, `distribution-prod.json`, `chunks-presign-upload-s3-policy.json.tmpl`.

**Terraform files are named by Terraform's convention, not this one** — `main.tf`, `variables.tf`, `outputs.tf`, `versions.tf`, `backend.tf`, `providers.tf`. The tool assigns meaning to those names, so they are not ours to choose. Directories under `infrastructure/terraform/` remain `kebab-case`, and an environment directory is named for the AWS slug (`dev`), per §7.1.

**Common mistake.** Using the `APP_ENV` key (`development`) where the AWS slug (`dev`) belongs, or the reverse. The two differ deliberately — see §7.1.

**Exceptions.** Files that are not per-environment carry no suffix: `environments.json`, `env.sh`, `apply-cloudfront.sh`.

## 2. Types

### 2.1 Classes

**Convention.** `PascalCase`, a noun or noun phrase. Enforced by `camel_case_types`.

**Why.** A class is a thing; a name that reads as an action (`ProcessData`) is a function wearing a class's clothes.

**The modifier carries meaning, and the three in use are not interchangeable:**

| Declaration | Means | Example |
|---|---|---|
| `abstract final class` | A namespace of `static const` members. Cannot be constructed, cannot be extended. | `AppColors`, `NetworkConstants`, `AppTheme` |
| `abstract class` | An extendable base with shared behaviour. | `AppException` |
| `abstract interface class` | A pure contract. Implement, never extend. | `Migration` |
| `final class` | A concrete type nothing may subclass. | `Failure` |
| `class` | A concrete type, extendable if it says so. | `DioClient`, `AppFeatureFlags` |

**Common mistake.** Using `abstract class` for a static holder. It leaves the class extendable, so someone eventually extends a namespace and adds instance state to it.

**Exceptions.** None. If a class does not fit one of the five, the design is unclear before the name is.

### 2.2 Abstract classes and interfaces

**Convention.** The name states the **role**, with no marker of abstractness. No `I` prefix, no `Abstract` prefix, no `Impl` suffix. The implementation is named for its **mechanism**.

**Why.** This is the pattern the codebase already uses and it is worth protecting: `SecureStorageRepository` is the interface `domain` and `application` depend on; `SecureStorageService` is the concrete class that talks to the platform keychain. The names describe what each *is*, so a second implementation is `SecureStorageInMemoryService`, not `SecureStorageRepositoryImpl2`. `IRepository`/`RepositoryImpl` encodes a language limitation from C# and Java into a codebase that has neither, and `Impl` tells the reader nothing about which implementation they are looking at.

**Examples.**

```
core/storage/interfaces/secure_storage_repository.dart   abstract interface → the contract
core/storage/secure_storage_service.dart                 implements it
core/database/migrations/migration.dart                  abstract interface class Migration
```

**Common mistake.** `ISessionRepository` / `SessionRepositoryImpl`. Also: putting the interface in the same file as its only implementation — it must be importable without the implementation, or ADR-022's `presentation/`↛`data/` rule cannot be honoured.

**Exceptions.** None.

### 2.3 Mixins

**Convention.** `PascalCase`, describing a **capability** — usually adjectival, ending `-able`, or a role noun ending `Mixin` only when no adjective reads naturally.

**Why.** A mixin is a property the class acquires, not a thing the class is. `Loggable` reads correctly at the use site (`class X with Loggable`); `Logger` reads as though the class *is* a logger.

**Examples.** `Loggable`, `Disposable`, `Comparable` (Dart's own).

**Common mistake.** Using a mixin where composition would do. A mixin adds to the public API of every class that uses it, permanently and invisibly at the call site.

**Exceptions.** None. No mixin exists in this repository yet, so this rule has no legacy to accommodate.

### 2.4 Extensions

**Convention.** Named, always. `<Type><Purpose>` in `PascalCase`. Enforced as `camel_case_extensions`; unnamed extensions are forbidden by ADR-023.

**Why.** An unnamed extension cannot be hidden, shown, or referred to in an import, so a name collision between two unnamed extensions on the same type is unresolvable without editing one of them. A name also makes the extension's purpose greppable.

**Examples.** `DatabaseMetadataQueryFilter`, `DatabaseMetadataQuerySortBy` — generated by `isar_generator`, and correctly named.

**Common mistake.** `extension on String { ... }`. Also: extending a type you own — if you can add the method to the class, add it to the class.

**Exceptions.** None.

### 2.5 Enums

**Convention.** `PascalCase` singular type name; `camelCase` members. Where an enum carries a string that crosses a boundary, that string lives in a `final String` field, not in the member name.

**Why.** The member name is a Dart identifier and must follow Dart conventions (`non_constant_identifier_names`); the wire value is a persisted or transmitted string whose format is fixed by the boundary it crosses. Keeping them separate lets either change without the other — renaming `ErrorCode.networkTimeout` is a refactor, changing `'NETWORK_TIMEOUT'` is a breaking API change.

**The two wire formats in use, and why they differ:**

| Enum | Wire format | Why |
|---|---|---|
| `ErrorCode` | `SCREAMING_SNAKE_CASE` — `'NETWORK_TIMEOUT'` | Appears in logs and API responses next to prose. Upper case makes it unmistakably an identifier rather than a phrase, and it is greppable across a log aggregator. |
| `StorageKey` | `snake_case` — `'access_token'` | These are keys in the OS keychain and Android `SharedPreferences`. Lower case with underscores is the platform convention, and it avoids the case-sensitivity differences between the two backends. |
| `AppEnvironment` | Three fields: `label` (`'Development'`), `key` (`'development'`), `slug` (`'dev'`) | Three different consumers — humans, `APP_ENV`, AWS. See §7.1. |

**Examples.**

```dart
enum ErrorCode { networkTimeout('NETWORK_TIMEOUT'), ... }
enum StorageKey { accessToken('access_token'), ... }
```

**Common mistake.** Naming the member in the wire format (`enum ErrorCode { NETWORK_TIMEOUT }`) — a lint failure and it welds the identifier to the protocol. The reverse mistake is deriving the wire value from the member name with a `.toString()` or a `name` getter, which turns every future rename into a silent protocol change.

**Exceptions.** An enum whose values never leave the process needs no wire field: `LogLevel` has a `label` because it is written to output; a purely internal enum would not.

### 2.6 Typedefs

**Convention.** `PascalCase`. Use for a function signature that appears in more than one public API. Do not use to alias a class.

**Why.** A typedef for a repeated callback signature (`typedef ChunkUploadProgress = void Function(int sent, int total);`) names a concept and gives one place to change it. A typedef aliasing a class creates a second name for one thing, so a reader cannot tell whether two APIs take the same type.

**Examples.** None exist yet in hand-written code. The rule is stated so the first one is right.

**Common mistake.** `typedef Json = Map<String, dynamic>;`. It looks tidy and hides the fact that the value is untyped — precisely what `strict-casts` and `avoid_dynamic_calls` (ADR-021) exist to surface.

**Exceptions.** None.

### 2.7 Generic type parameters

**Convention.** Single uppercase letters, by role: `T` for the one type, `K`/`V` for a map's key and value, `R` for a result, `E` for an element or error. More than three parameters, or a parameter whose role is not obvious, gets a descriptive `PascalCase` name.

**Why.** `T` is universally understood and adds no reading cost; `TItem` adds a prefix that means nothing in Dart. Beyond three, single letters stop being mnemonic and a descriptive name is cheaper than a lookup.

**Examples.** `Provider<ThemeMode>`, `ThemeExtension<AppSemanticColors>`, `Future<T>`.

**Common mistake.** Reusing `T` for two unrelated parameters in nested generics, so the inner shadows the outer — `avoid_shadowing_type_parameters` (ADR-021) catches this.

**Exceptions.** None.

## 3. Suffix vocabulary

**Convention.** The suffix of a type name is a **contract about what the type is**. The vocabulary is closed: use one of these or none.

**Why.** This is the single most valuable naming rule in the document, because it is the one a reader relies on without checking. If `SessionRepository` might be an interface or might be a concrete Dio caller, the suffix carries no information and every reader must open the file. A closed vocabulary also makes ADR-022's import rules readable at the import line: `import '...session_repository.dart'` in `application/` is fine, `...session_remote_data_source.dart` is not.

| Suffix | Is | Layer | Example |
|---|---|---|---|
| *(none)* | A domain entity — a noun from the business vocabulary | `domain/` | `Session`, `Chunk`, `Task` |
| `Repository` | An **interface** declaring what the domain needs | `domain/` (declared) | `SecureStorageRepository`, `SessionRepository` |
| `UseCase` | One operation, one entry point | `application/` | `StartRecordingUseCase` |
| `Dto` | A wire or storage shape. Never leaves `data/` | `data/` | `SessionDto` |
| `DataSource` | A single I/O boundary — one API, one table | `data/` | `SessionRemoteDataSource` |
| `Mapper` | Converts between a `Dto` and an entity | `data/` | `SessionMapper` |
| `Service` | A concrete mechanism that performs work | `core/`, `data/` | `SecureStorageService`, `DatabaseService` |
| `Client` | A thin wrapper over one third-party transport | `core/` | `DioClient` |
| `Config` | Resolved, immutable settings | anywhere | `NetworkConfig`, `DatabaseConfig` |
| `Constants` | An `abstract final class` of `static const` values | anywhere | `NetworkConstants`, `DatabaseConstants` |
| `Exception` | A thrown internal failure | `core/`, `data/` | `NetworkException`, `StorageException` |
| `Screen` | A routed, full-screen destination | `presentation/` | `HomeScreen` |
| `Controller` | Presentation state holder (a Riverpod notifier) | `presentation/` | `RecordingController` |
| `Interceptor` | A hook in a request pipeline | `core/network/` | `AuthInterceptor` |
| `Initializer` | Brings a platform up exactly once | `core/` | `FirebaseInitializer` |
| `Runner` | Executes an ordered sequence | `core/` | `MigrationRunner` |

**Common mistakes.**

- **`Manager`, `Helper`, `Handler`, `Util`, `Wrapper`, `Processor`, `Provider` (as a class suffix).** All forbidden. Each means "this class does something", which is true of every class. `Manager` in particular is where responsibilities accumulate, because nothing is obviously out of scope for a thing called a manager.
- **`Model`.** Forbidden, and no type in this repository uses it. It is ambiguous across all four layers — a "model" may be an entity, a DTO or view state — so it defeats the purpose of the vocabulary. Say `Dto`, or say nothing and have an entity.
- **`Service` in `domain/`.** A domain type that performs work is either an entity method or a use case. `domain/` has no I/O (ADR-022 §3.1), so it has nothing to service.
- **`Repository` on a concrete class.** The interface takes the role name; the implementation takes its mechanism (§2.2).

**Exceptions.** `Page` is not used — this project says `Screen`, consistently, and mixing the two means guessing per feature. Legacy Flutter samples use `Page`; we do not.

## 4. Riverpod providers

### 4.1 Provider variables

**Convention.** `camelCase`, `<subject>Provider`, declared as a top-level `final` with an explicit type. The file is `<module>_provider.dart` in the owning module's `providers/` directory.

**Why.** The `Provider` suffix is the one place a role suffix belongs on a variable rather than a type: at a call site, `ref.watch(dioClientProvider)` must be distinguishable from a `DioClient` instance, and without the suffix a reader cannot tell whether `dioClient` is the value or the recipe. The explicit type is required by `always_specify_types` (ADR-021) and does real work here — it is what makes `Provider<SecureStorageRepository>` announce that consumers get the *interface*.

**Examples.**

```dart
final Provider<DioClient> dioClientProvider = ...
final FutureProvider<Isar> databaseProvider = ...
final Provider<SecureStorageRepository> secureStorageProvider = ...
```

**A file may hold several providers.** `core/network/providers/dio_provider.dart` holds `networkConfigProvider`, `dioClientProvider` and `dioProvider`; `database_provider.dart` holds six. This is the deliberate exception to one-public-declaration-per-file: a provider is a wiring statement, not a type, and splitting one module's wiring across six files hides the dependency graph that is the whole point of reading it.

**Common mistakes.**

- Doubling the suffix — `dioClientProviderProvider`.
- Naming the provider for its **type** rather than its **subject**: `futureProvider`, `stringProvider`.
- Naming it for the implementation when it exposes an interface. `secureStorageProvider` returns `SecureStorageRepository`, and is correctly *not* called `secureStorageServiceProvider` — the name promises the contract, so swapping the implementation is not a rename at every call site.

**Exceptions.** None.

### 4.2 Notifiers and controllers

**Convention.** The notifier class is `<Subject>Controller`; its provider is `<subject>ControllerProvider`.

**Why.** `Controller` is already the suffix for presentation state (§3), and repeating it in the provider name keeps the pairing obvious. The alternative — `<subject>Provider` for a notifier — collides with the plain-value providers of §4.1, so a reader cannot tell whether `recordingProvider` yields a value or a mutable notifier.

**Examples.** `RecordingController` → `recordingControllerProvider`.

**Common mistake.** `RecordingNotifier`/`RecordingViewModel`/`RecordingBloc`. ADR-003 makes Riverpod the sole mechanism; borrowing another framework's vocabulary implies a second one is in play.

**Exceptions.** None. No notifier exists yet.

## 5. Members

### 5.1 Methods

**Convention.** `camelCase`, starting with a **verb**. A getter is a noun. Two patterns are established for deriving a value from an environment:

- `static X <subject>For(AppEnvironment)` — derives **one value**: `baseUrlFor`, `chunkBucketFor`, `minimumLevelFor`.
- `factory X.forEnvironment(AppEnvironment)` — derives a **value object**: `NetworkConfig.forEnvironment`, `AppFeatureFlags.forEnvironment`.

**Why.** The verb is what distinguishes a method from a field at the call site. The `For`/`forEnvironment` split tells the reader the shape of what comes back before they read the return type, and it keeps the enum-exhaustive `switch` — the thing that makes adding an environment a compile error rather than a silent default — in one recognisable place.

**Examples.** `open()`, `close()`, `apply(isar)`, `read(key)`, `write(key, value)`, `describe()`, `isEnabled`, `shouldLog(level)`, `isAtLeast(other)`.

**Common mistakes.**

- `getUser()` where `user` would do. Dart has getters; `get` prefixes are noise.
- A boolean method without a predicate prefix. Use `is`, `has`, `should`, `can` — `isAtLeast`, `shouldLog`, `firebaseFailureIsFatal`.
- A getter that does work. A getter must be cheap and side-effect-free; a reader assumes a field. `recursive_getters` (ADR-021) catches only the pathological case.

**Exceptions.** Overrides keep the name of what they override — `toString`, `build`, `lerp`, `onRequest`. Package-imposed names (`copyWith`) are not renamed.

### 5.2 Variables and parameters

**Convention.** `camelCase`, with the type annotated (`always_specify_types`) and `final` wherever it is not reassigned (`prefer_final_locals`). Parameters at any public boundary are **named**, not positional.

**Why.** Named parameters make a call site self-documenting and reorderable, and they are what makes `avoid_positional_boolean_parameters` (ADR-021) satisfiable — `save(true, false)` says nothing. Every constructor in `core/` already uses `{required this.x}`.

**Examples.** `final ProviderContainer container = ProviderContainer();`, `NetworkConfig({required this.baseUrl})`.

**Common mistakes.** Abbreviations that save four characters and cost a lookup — `cfg`, `env`, `mgr`, `res`. Loop and closure variables named `e` where the type is not obvious; `catch (error, stackTrace)` is spelled out throughout `core/` for exactly this reason.

**Exceptions.** `i` in a numeric `for`, and the conventional single-letter parameter of a short mathematical closure (`lerp(other, t)`).

### 5.3 Constants and static members

**Convention.** `camelCase`, never `SCREAMING_SNAKE_CASE`. Grouped as `static const` members of an `abstract final class <Domain>Constants`.

**Why.** `constant_identifier_names` (ADR-021) enforces `camelCase` — Dart abandoned the SCREAMING convention because a `const` is an implementation detail of how a value is stored, not a different kind of name. Grouping in a named holder means the constant is always read with its domain attached: `NetworkConstants.redactedPlaceholder`, never a bare `redactedPlaceholder` imported from nowhere.

**Examples.** `AppConstants`, `NetworkConstants`, `DatabaseConstants`, `FirebaseConstants`; members like `defaultAppName`, `redactedHeaders`, `borderMd`.

**Common mistakes.** `const MAX_RETRIES = 3;` — a lint failure. A top-level `const` outside a holder, which becomes an unqualified name at the use site. A holder named `Constants` with no domain, which is `utils/` in class form.

**Exceptions.** The **string values** those constants hold follow the boundary's convention, not Dart's — `ErrorCode`'s `'NETWORK_TIMEOUT'` is `SCREAMING_SNAKE_CASE` because the API says so (§2.5). The identifier and the value are separate decisions.

### 5.4 Private members

**Convention.** Leading underscore, then `camelCase` for members and `PascalCase` for types. Private by default: add the underscore unless something outside the library needs it.

**Why.** In Dart, privacy is per-library, so the underscore is the only access control there is — and it is what lets `unused_element` (an error under ADR-021) prove a member is dead. A private member can be renamed or deleted with confidence; a public one cannot.

**Examples.** `_guard`, `_opening`, `_redactHeaders`, `_announceEnvironment`, `class _ThresholdFilter extends LogFilter`.

**Common mistake.** Making a member public so a test can reach it. Test the public behaviour, or the design has a seam in the wrong place — `SecureStorageService` is tested through `SecureStorageRepository`, not through `_guard`.

**Exceptions.** `use_late_for_private_fields_and_variables` (ADR-021) applies only to private fields, which is another reason the default matters.

## 6. Widgets, screens and routes

### 6.1 Widgets and screens

**Convention.** A routed, full-screen destination is `<Subject>Screen`. Any other widget is named for what it is, with no suffix. Both `PascalCase`.

**Why.** `Screen` marks the small set of widgets that a route points at, which is exactly the set that `app/router.dart` may import under ADR-022's router exception. Everything else is a component, and `SessionCardWidget` is longer than `SessionCard` while saying the same thing — in a Flutter codebase, being a widget is the default.

**Examples.** `HomeScreen` in `presentation/screens/`; a `SessionCard` in `presentation/widgets/`.

**Common mistakes.** `HomePage` — this project says `Screen`, everywhere (§3, exceptions). A `Widget` suffix. Naming a screen for its route (`RootScreen`) rather than its content.

**Exceptions.** None.

### 6.2 Routes

**Convention.** Path is lowercase `kebab-case`, starting `/`. Multi-word segments hyphenate; path parameters are `:camelCase`. Where a path needs a constant, it is a `static const String` on the screen's own class or a route-name holder — never a bare literal at a `context.go` call site.

**Why.** ADR-004 requires navigation by path, so paths are typed at call sites and a typo is a runtime failure rather than a compile error. Naming them once, in a constant, converts that class of bug back into a compile error. Lowercase kebab-case is the URL convention and matches the ADR-015 Lambda names (`auth-verify`), so a route and its endpoint read alike.

**Examples.** `/`, `/recording`, `/tasks/:taskId`, `/settings/legal-hold`.

**Common mistakes.** `camelCase` or `snake_case` in a path — both are unconventional in URLs, and a screen deep-linked from a notification then has a URL nobody can dictate over the phone. A trailing slash, which GoRouter treats as a distinct path.

**Exceptions.** `/` for the root.

## 7. Environments and external resources

### 7.1 Environment names

**Convention.** Three environments, and **three distinct spellings for three distinct consumers** — already fixed by ADR-007, ADR-011 and ADR-014, and carried by `AppEnvironment`:

| Field | Value | Consumed by |
|---|---|---|
| `label` | `Development` / `Staging` / `Production` | Humans — diagnostics, debug surfaces |
| `key` | `development` / `staging` / `production` | `APP_ENV`, `.env` files, `environments.json` |
| `slug` | `dev` / `staging` / `prod` | AWS resource names |

**Why the slug differs from the key.** The buckets are `vump-platform-dev`, not `vump-platform-development`, and **S3 bucket names are immutable** — so the divergence is a fact about existing infrastructure, not a preference. `AppEnvironment` holds all three so that no call site has to know which one a given consumer wants.

**Common mistake.** Using `key` where `slug` belongs, producing a bucket name that does not exist. This is why `EnvironmentProfile` (ADR-018) is the single read surface: it delegates, so there is one definition of each spelling.

**Exceptions.** None. Adding a fourth environment means adding it to the enum, which is a compile error at every exhaustive `switch` — by design.

### 7.2 S3 buckets and object keys

**Convention.** Fixed entirely by ADR-011 and ADR-012: buckets are `vump-platform-{slug}`; the object key schema is

```
{org_id}/{project_id}/{task_id}/{session_id}/{sequence_index:04d}_{chunk_id}.mp4
```

**Why this is not restated here.** ADR-011 is the authority, the key schema is confirmed authoritative in the amendment register, and bucket names cannot be changed. Duplicating them would create a second copy to fall out of date.

**One naming note that belongs here.** The key placeholders are `snake_case` because they are path segments corresponding to Aurora columns (§7.5), not because JSON is `snake_case` (§7.4). The two conventions are independent and both are deliberate.

### 7.3 Firebase resources

**Convention.** One Firebase project per environment, named `vump-platform-{slug}`. The Dart-side app name is the platform default, held as a constant: `FirebaseConstants.defaultAppName = '[DEFAULT]'`.

**Why.** ADR-010 requires initialisation exactly once, and `[DEFAULT]` is the name the native SDKs use for the implicitly-created app — restating it as a literal at each call site would make a typo a runtime lookup failure.

**Known gap, not a naming exception.** Only one project exists, `vump-platform-f86af` (Firebase appends its own uniqueness suffix), and it serves all three environments — so production analytics and auth users are indistinguishable from development ones. Tracked as amendment **A-014**; closing it means running `flutterfire configure` against two further projects. The naming rule above is the target, not the current state.

**Common mistake.** Hard-coding a project ID in Dart. It belongs in the generated `firebase_options.dart` and is exposed through `EnvironmentProfile.firebaseProjectId`.

### 7.4 API endpoints and JSON fields

**Convention.**

- **Paths** — lowercase, plural resource nouns, `kebab-case` for multi-word segments, version first: `/v1/sessions`, `/v1/sessions/{sessionId}/chunks`, `/v1/auth-verify`.
- **Wire JSON fields** — `camelCase`, request and response alike.

**Why.** ADR-015 fixes the Lambda decomposition as `auth-verify`, `projects`, `tasks`, `sessions`, `chunks`, `metadata` — plural resource nouns in kebab-case — so paths that mirror those names need no translation table between a URL and the function that serves it.

`camelCase` on the wire is chosen because **two of the three surfaces are already `camelCase`-native**: the backend is TypeScript (ADR-015) and the client is Dart. Aurora is `snake_case` (§7.5), so exactly one rename is unavoidable; putting it in the backend — one typed layer, one place — is cheaper than a `@JsonKey` on every field of every Dart DTO, where each omission is a silent null. `infrastructure/aws/config/environments.json` already uses `camelCase` (`chunkBucket`, `presignExpirySeconds`), so this is consistent with the only JSON the repository has.

**Examples.** `{"sessionId": "...", "sequenceIndex": 12, "chunkBucket": "vump-platform-prod"}`.

**Common mistakes.** Mixing conventions per endpoint, which forces a per-endpoint `fieldRename` and guarantees one gets it wrong. Renaming a field in Dart with `@JsonKey` to "tidy" a name — the wire format is a contract, and a local rename hides a mismatch that then only appears at runtime.

**Exceptions.** Fields defined by a third party keep their format — a Firebase ID token's claims (`iss`, `aud`, `exp`) are not renamed.

### 7.5 Database — Aurora and Isar

**Aurora (PostgreSQL).** `snake_case` for tables and columns, tables plural: `chunk_metadata`, `audit_log`, `legal_hold_at`. **Why:** unquoted identifiers in PostgreSQL fold to lower case, so a `camelCase` column must be quoted forever or silently becomes `camelcase`. The names already in use in Volume 8 §8.7 and the amendment register follow this.

**Isar collections.** The `@collection` class is a `PascalCase` **singular** entity name; the file is its `snake_case` form, in `core/database/collections/` or the feature's `data/`. Isar derives the stored collection name from the class name.

**Why singular.** A collection class describes one record — `DatabaseMetadata` is the metadata of one database — and Isar's generated API reads correctly that way (`isar.databaseMetadatas` is Isar's plural, not ours).

**Common mistake — and it is a data-loss mistake.** Using `@Name` to rename a collection or property. Isar identifies stored data by that name, so changing it is a schema migration, not a rename; without one, the old data becomes unreachable. Get the name right when the collection is created.

**Exceptions.** None.

### 7.6 Migration files

**Convention.** One file per migration, `migration_v<from>_to_v<to>.dart`, containing `class MigrationV<From>ToV<To> implements Migration`, in `core/database/migrations/`.

**Why.** `Migration` declares `int get from` and `int get to` (ADR-009), so the file name states exactly the two facts `MigrationRunner` orders by — and it sorts correctly in a directory listing as long as versions stay single-digit, with the class name making the endpoints unmissable in a stack trace. A name carrying only one version (`migration_v2.dart`) is ambiguous about whether 2 is the source or the target.

**Examples.** `migration_v1_to_v2.dart` → `class MigrationV1ToV2 implements Migration`.

**Common mistakes.** A date prefix (`20260811_add_index.dart`) — the schema version is the ordering key here, not wall-clock time, and two developers can date-collide. Describing the change instead of the versions (`add_session_index.dart`), which loses the ordering the runner depends on.

**Exceptions.** None. No migration exists yet; `migration.dart` is the interface and `migration_runner.dart` the executor, neither of which is a migration.

## 8. Tests

**Convention.**

- **File** — `<subject>_test.dart` at the mirrored path (§1.3).
- **`group`** — the area or behaviour under test, as a noun phrase. Nest freely.
- **`test` / `testWidgets`** — a lowercase sentence stating **the guarantee**, readable as a claim that is either true or false.

**Why.** A failing test prints `group name > test name`, and that concatenation is the entire error message a developer sees first. `EnvironmentProfile exposes every required value > for all three environments, nothing is missing or empty` tells you what broke. `EnvironmentProfile > test1` does not, and neither does `should return correct value`.

**"should" is dropped deliberately.** It is filler on every line — the sentence is already a claim — and it pushes the writer toward describing the implementation rather than the guarantee.

**Examples**, from the existing suite:

```dart
group('APP_ENV resolution', () {
  test('an undeclared APP_ENV resolves to development', ...);
  test('keys are exactly the three documented tokens', ...);
});
group('the profile delegates and never defines', () {
  test('apiBaseUrl equals the owner NetworkConfig', ...);
});
```

**Common mistakes.** Naming the test after the method (`test('baseUrlFor')`) — the name should survive a rename of the method, because it describes behaviour. Starting with a capital, which reads oddly once concatenated with the group. Asserting several unrelated guarantees in one test, at which point no single sentence can name it.

**Exceptions.** `testWidgets` follows the same rule; the widget's name may lead the sentence where it is the subject — `HomeScreen displays the application name and mission status`.

## 9. Documentation and commits

### 9.1 Markdown headings

**Convention.** **Sentence case** — capitalise the first word and proper nouns only. One `#` per document, as the title. Headings are noun phrases, not questions.

**Why.** Sentence case is what the majority of this repository's prose documents already use (`secrets-management.md`, `disaster-recovery.md`, `infrastructure/aws/README.md`, `folder-structure.md`), it reads as prose rather than as a label, and it removes the per-heading judgement call about whether a short word gets a capital.

**Examples.** `## Repository folder structure`, `## Why these files exist rather than console clicks`, `### Adding a feature`.

**Common mistake.** Title Case, which requires deciding about every "of", "the" and "to".

**Exceptions, both real.**

1. **ADR section headings are fixed verbatim.** `## Context`, `## Decision`, `## Alternatives Considered` and `## Consequences` come from the template in `docs/architecture/README.md`; `## Related Missions` and `## Implementation Status` are not in that template but have been used consistently since ADR-019 and are now equally fixed. All six are template slots rather than choices, so the three that are Title Case stay Title Case — consistency across 23 ADRs matters more than the case rule, and a reader scanning for `## Decision` should never have to guess its capitalisation.

   Free-text headings *within* an ADR section — the `###` subheadings this document and ADR-022 use inside `## Decision` — follow sentence case like any other prose.
2. **Pre-existing Title Case documents are not rewritten by this mission.** `docs/architecture/README.md` and `docs/git/*.md` use Title Case throughout. Renaming their headings would be a large diff on files this mission was not asked to change, for zero behavioural gain. They are normalised when next edited for another reason. Recorded in §11.

### 9.2 Commit references

**Convention.** Fixed by ADR-020 and `docs/git/commit-conventions.md` — `type(scope): subject`, with a closed set of types and scopes matching the repository structure.

**The one naming point that belongs here:** the **scope** is a path fragment, not a free-text label — `core/network`, `app/theme`, `features/recording`, `docs/adr`. It matches the folder the change touches, so `git log --grep` over a scope is a reliable history of that directory. A scope that names a *concept* rather than a *directory* breaks that.

**Footer references** use the identifier's own format: `Implements ADR-020`, `Constrained by ADR-007`, `Implements FR-CHK-05`, `Closes #142`, `Reverts: <sha>`.
